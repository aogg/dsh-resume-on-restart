# 被注入说明：重启后恢复会话时投递的提示词

> 版本：0.32.0 起（分段抽出 `noticeSegments`，输出与 0.31.x 逐字一致）。
> 适用对象：想弄清「重启后模型到底收到了什么、为什么它会自己继续」的用户与插件作者。
>
> - 文案构建：`lib/detect.js` 的 `noticeSegments()` / `buildNotice()`
> - 消息外壳：`lib/detect.js` 的 `createNoticeMessage()`
> - 投递：`lib/index.js` 的 `deliver()`
> - 在界面上看：设置弹窗 → 重启 → **技能展示** tab → 「重启后恢复会话的提示词」区块
> - 扩展点（不是本文）：[docs/被扩展说明.md](./被扩展说明.md)

---

## 1. 一句话

重启完成后，本插件把每个**恢复成功**的会话（`sessionController.resolveAgent` 拉起成
live agent）各投递**一条普通 user 消息**：正文以 `[resume-on-restart] 检测到 DSH 服务
已重启。` 开头，中间是这次重启的事实（上次运行时间、中断时长、最近活跃会话、恢复了
哪些会话），最后一行固定要求模型「自主决定下一步」。模型收到这条消息后，接着之前的
工作干 —— 这就是「重启后自动继续」的全部机制，没有隐藏的 system prompt，也没有魔法
指令。

---

## 2. 投递时机与对象

```
检测到重启（wasRestart）→ 写 boot 记录 → 挑候选（排除/归档/正常结束门过滤）
  → 逐候选：resolveAgent 拉起 → 生成提示词 → target.followup(msg) / target.inject(msg)
  → 全部失败才 fallback：向 config.target 解析出的主会话投一条（同样文案）
```

- **自动投递只发生在重启后的开机流程**（`wasRestart === true` 且
  `restoreSessions !== false`）；普通启动不打扰任何会话。唯一的手动例外是用户在
  「上次重启无法恢复」列表里点「恢复」（`POST /unrestored/restore`）——那也走同一条
  `deliver()`，文案一致。
- **每个恢复成功的会话一条**，正文里的「已自动恢复…会话 X」对每个会话是自己的 id。
  多会话恢复时，每个会话各自收到一条只讲自己的消息；一次都恢复不出来时才 fallback
  向主会话投一条（那条没有「已自动恢复」行）。
- 以下情况**不会**投递：
  - 会话被用户排除（顶栏开关 / 待恢复列表「取消」）、已归档、最后状态是「正常结束」；
  - 会话没有过真实人工输入（`requireHumanPrompt` 守卫，fail-closed）；
  - `register_restart_recovery` 登记为「注册但不激活」（`activate: false`）；
  - 服务始终没就绪 / 预算耗尽（记 `skipped-budget` / `skipped-service-timeout`）；
  - 本轮自动恢复被扩展点 `before-resume` 取消（见 [被扩展说明](./被扩展说明.md)）。
- 续等补跑、`POST /unrestored/restore` 手动恢复，投递的是**同样的文案**（同一条
  `deliver()` 实现）；已投递过的会话按 `deliveredTo` 去重，不重复投递。
- 候选会话**已经是 live**（例如用户已经手动打开）→ 不再 `resumeSession`，但仍然投递这条
  消息（「已 live 直接投递」是既有行为，等于告诉它「刚重启过，接着干」）。同一会话在一次
  boot 内按 `deliveredTo` 去重：续等补跑、fallback、手动恢复都不会二次投递；手动恢复时
  若会话本就 live，则记 `session already live, notice not re-delivered` 直接按成功处理。

## 3. 消息外壳（不是纯文本那么自由）

投递的不是字符串，而是宿主会话格式认可的消息对象（`createNoticeMessage`）：

```json
{
  "role": "user",
  "content": [{ "type": "text", "text": "<第 4 节的正文>" }],
  "source": {
    "kind": "dsh-resume-on-restart",
    "form": "notice",
    "summary": "resume-on-restart: DSH restarted at 2026-11-07T04:03:52.490Z"
  },
  "id": "<随机 UUID>"
}
```

- `role: 'user'`：它是一条用户消息（对模型来说等同于有人说了这段话），不是 system。
- `source.kind` 必须是**生产者自己的名字**且不能是 `'plugin'`（会话格式 v4 的准入规则，
  写成 `{ kind: 'plugin' }` 会被 `SessionFormatError` 拒收、投递一直失败）。
- `source.form: 'notice'` + `source.summary` 是给宿主/日志识别用的标记：会话里能看出
  这条消息由本插件在重启后注入。
- 投递通道由配置项 `wakeup` 决定：
  - `wakeup: true`（默认）→ `agent.followup(msg)`：作为**新回合**投递，模型会被唤醒执行；
  - `wakeup: false` → `agent.inject(msg)`：注入当前回合（不新起回合，仅在上下文里可见）。

## 4. 正文模板（逐行）

正文由 `noticeSegments()` 按固定顺序拼装，**空片段（条件不满足）不出现**，最后
`join('\n')`。下列 `${...}` 是变量，`⟂` 表示该行不出现：

| # | key | 模板 | 出现条件 | 数据来源 |
| --- | --- | --- | --- | --- |
| 1 | `header` | `[resume-on-restart] 检测到 DSH 服务已重启。` | 恒有 | 常量 |
| 2 | `boot` | 有上次启动：`上次运行于 ${prevBootAt}，本次于 ${bootAt} 重启完成。`<br>没有：`本次于 ${bootAt} 启动。` | 恒有 | `prevBootAt` = 上次 marker 的 `lastBootAt`；`bootAt` = 本次启动时刻 |
| 3 | `downtime` | `中断约 ${humanizeDowntime(downtimeMs)}。` | `downtimeMs > 0` | `detectRestart` 算出的「上次启动 → 本次启动」间隔；文案为中文「N 秒 / N 分 M 秒 / N 小时 M 分」 |
| 4 | `lastSession` | `重启前最近活跃的会话：${lastSessionId}` | 上次 marker 有 `lastSessionId` | marker |
| 5 | `lastActive` | `该会话最后活跃于 ${lastActiveAt}。` | 且有 `lastActiveAt` | marker |
| 6 | `restored` | 有最后活跃时刻：`已自动恢复重启前活跃的会话 ${restoredSessionId}（最后活跃于 ${restoredActiveAt}）。`<br>没有：`已自动恢复重启前活跃的会话 ${restoredSessionId}。` | 本次**确实恢复了**这个会话（`deliver(agent, restored)` 传了 `restored`） | 候选条目 `id` / `at`（epoch ms → ISO；`at <= 0` 时走无括号形态） |
| 7 | `custom` | `config.notice` 原文 | 插件配置 `notice` 非空 | `cordis.patch.yml` 的 `notice` |
| 8 | `tail` | `如需继续之前的工作，或启动新任务，请自主决定下一步。` | 恒有 | 常量 |

片段 key 白名单是 `NOTICE_SEGMENT_KEYS`（`lib/detect.js` 导出，`lib/notice.test.js`
校验它与客户端 i18n 文案一一对应）；`buildNotice()` 就是
`noticeSegments().map(s => s.text).join('\n')`，两者输出逐字一致。

> 注意第 6 行的标点：带括号形态是「……会话 X（最后活跃于 T）。」，不带括号是
> 「……会话 X。」——括号包住整个补充说明，句末仍是中文句号。

## 5. 一份真实样本

`prevBootAt` / `downtimeMs` / `lastSessionId` / 恢复行都命中的典型重启（多行原文）：

```
[resume-on-restart] 检测到 DSH 服务已重启。
上次运行于 2026-11-07T03:59:44.001Z，本次于 2026-11-07T04:03:52.490Z 重启完成。
中断约 4 分 8 秒。
重启前最近活跃的会话：session-0d8f5d2c-1f7a-4a0f-9c33-0d2f6b8f0c11
该会话最后活跃于 2026-11-07T03:59:41.512Z。
已自动恢复重启前活跃的会话 session-0d8f5d2c-1f7a-4a0f-9c33-0d2f6b8f0c11（最后活跃于 2026-11-07T03:59:41.512Z）。
如需继续之前的工作，或启动新任务，请自主决定下一步。
```

最小形态（普通启动、无中断、无恢复；`buildNotice({ bootAt })` 的逐字输出）：

```
[resume-on-restart] 检测到 DSH 服务已重启。
本次于 2026-11-07T04:03:52.490Z 启动。
如需继续之前的工作，或启动新任务，请自主决定下一步。
```

---

## 6. 为什么这样写

| 写法 | 意图 |
| --- | --- |
| 首行 `[resume-on-restart] …` | 归属标记：用户/日志一眼看出这条消息来自本插件，不是用户本人发的 |
| `上次运行于 …，本次于 …` | 给模型时间线：它被打断了多久、这是一次重启而不是普通新会话 |
| `中断约 N` | 让模型判断「之前的上下文是否还新鲜」，必要时重读文件 |
| `重启前最近活跃的会话：…` | 指明「你就是那个被打断的会话」（多会话场景下给出身份） |
| `已自动恢复重启前活跃的会话 X` | 让模型知道自己是被本插件重新拉起的，不是用户新开的窗口 |
| `config.notice` 自定义行 | 站点级附加提醒（例如团队规范、迁移中提示） |
| 末行「如需继续之前的工作，或启动新任务，请自主决定下一步。」 | **「继续」的真正来源**：不是命令，而是一句让模型自主决策的收尾；模型据此回看上下文继续干活 |

它刻意**不**做这些事：不复述被中断的对话内容（那在会话历史里）、不指定具体下一步
（避免替模型做决定、也避免旧计划已失效时误执行）、不写成 system 角色（保持它是一条
可见的用户消息，用户可以在会话里看到并纠正）。

## 7. 怎么在界面上确认「现在到底会写什么」

设置弹窗 → 重启 → **技能展示** tab 最下方「重启后恢复会话的提示词」区块：

- **实际正文（本次启动数据渲染）**：用当前进程的 `bootAt` / `prevBootAt` / `downtimeMs`
  / `lastSessionId` / `lastActiveAt` + 最近一次恢复成功的会话渲染出的真实正文；
- **逐行来源与出现条件**：第 4 节那张表的界面版（每个 key 一行，标出本次是否出现）；
- **投递方式**：`followup` / `inject`、消息 `source`、`config.notice` 当前值。

数据来自只读路由 `GET /api/dsh-resume-on-restart/notice`：

```json
{
  "ok": true,
  "plugin": "dsh-resume-on-restart",
  "bootAt": "…", "prevBootAt": "…", "downtimeMs": 248000,
  "restoredSessionId": "session-…",
  "sample": "<第 4 节渲染出的完整正文>",
  "segments": [{ "key": "header", "text": "…" }, { "key": "downtime", "text": null }],
  "delivery": {
    "method": "followup", "wakeup": true, "role": "user",
    "source": { "kind": "dsh-resume-on-restart", "form": "notice", "summary": "resume-on-restart: DSH restarted at …" },
    "customNotice": null
  }
}
```

- `segments` 恒为**白名单全量**（8 条），本次不出现的片段 `text` 为 `null`——界面据此
  显示「本次未出现」，所以你能看到全部可能形态，而不只是这次恰好出现的那几行。
- 路由 404 = 插件已更新但 DSH 尚未重启（混合版本窗口）：界面显示「重启 DSH 后可见」。
- 围栏与本插件其余路由一致（同 Host/Origin 校验；未认证 401、不可信来源 403）。

## 8. 定制

| 想改什么 | 怎么做 |
| --- | --- |
| 追加一句自己的提醒 | 配置 `notice: '…'`（会作为第 7 行插在恢复行之后、末行之前） |
| 只要注入不要唤醒 | `wakeup: false`（改成 `agent.inject`，不新起回合） |
| 不让空会话被打扰 | 保持 `requireHumanPrompt: true`（默认，fail-closed） |
| 不恢复某些会话 | 顶栏开关 / 待恢复列表「取消」/ 归档 / `register_restart_recovery { activate: false }` |
| 整个提示词不投递 | 目前没有关闭开关：把 `restoreSessions: false` 关掉自动恢复，或让某个插件在 `before-resume` 返回取消值（见 [被扩展说明](./被扩展说明.md)） |
| 彻底换文案 | 改 `lib/detect.js` 的 `noticeSegments()`（注意 `lib/detect.test.js` 有逐字断言，`lib/notice.test.js` 有 key ↔ i18n 对齐断言） |

## 9. 排障

| 现象 | 排查 |
| --- | --- |
| 会话被恢复但模型没继续 | `wake.log` 里该会话是否有成功记录（`ok: true`）；`wakeup: false` 时只是 inject，不会新起回合 |
| 完全没有任何注入 | 是否真的重启（`restarts.ndjson` 有 boot 记录）？`reason` 是 `crash` 还是 `signal`？候选是否全被排除/归档/正常结束门挡下（restore 结算里有 `excluded` / `archived` / `skipped-completed`）？ |
| 投递失败 | `wake.log` 的 `error` 字段（常见：`source.kind === 'plugin'` 之类的会话格式校验、agent 尚未就绪） |
| 收到两条一样的 | 不应发生：`deliveredTo` 去重覆盖续等补跑与 fallback；若出现请带 `wake.log` 反馈 |
| 想知道「本该写什么」 | 看设置弹窗「技能展示」→ 提示词区块，或直接 `GET /api/dsh-resume-on-restart/notice` |
