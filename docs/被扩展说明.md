# 被扩展说明：其它插件如何挂进「重启」与「恢复会话」流程

> 版本：0.32.0 起。适用对象：想在本插件重启 DSH 之前收尾自己状态、或想在本插件
> 自动恢复会话之前拦一下/做准备的**其它 DSH 插件**。
>
> - 事件派发原语与取消口径：`lib/hooks.js`
> - 两个接线点：`lib/index.js`（`performRestart` 与开机恢复 IIFE）
> - UI 展示：`lib/client.js`（重启日志的「恢复已取消」、tab「技能展示」）
> - 投递什么文案（不是扩展点）：[docs/被注入说明.md](./被注入说明.md)

---

## 1. 两个扩展点一览

| 事件名（cordis） | 触发时机 | 每次重启/开机触发次数 | 取消的后果 |
| --- | --- | --- | --- |
| `resume-on-restart/before-restart` | 重启**被调用之后、真正开始重启之前**（按钮 / `/restart` 命令 / `restart_harness` 工具 / 注册后守门自动重启，四个入口共用同一处） | 每个重启请求一次 | 本次重启整体取消：不写重启工件、不 spawn helper、进程继续活着 |
| `resume-on-restart/before-resume` | 检测到本次启动确实是一次重启（`wasRestart`）、停机归因与 boot 记录落盘之后，**挑选恢复候选与恢复会话之前** | 每次开机一次（服务慢启动后的「续等补跑」不重复触发） | 本次自动恢复整体取消：不挑候选、不 `resumeSession`、不投递继续提示、不做 fallback 唤醒 |

两者都是**串行**事件（`ctx.serial`）：按监听器注册顺序**逐个 await**，前一个处理器的
Promise resolve 之后才轮到下一个；全部跑完且都没有取消，才继续本插件的原有逻辑。

---

## 2. 为什么是 cordis 事件

本插件不自造注册表，直接用宿主的事件总线：

- **生命周期自动托管**：监听器挂在注册它的插件 fiber 上，插件禁用/卸载/热重载时
  自动摘除，不会留下悬挂回调。
- **零耦合**：不需要 `inject: ['resumeOnRestart']`，不需要依赖本包，甚至不需要
  import —— 事件名是普通字符串（想避免手写漂移可以用常量，见下）。
- **与宿主口径一致**：取消值判定照抄 cordis 的 `isBailed`（`null` / `false` /
  `undefined` 不算 bail），和宿主的 `tools/pre-execute`、`llm/stream` 等钩子同一套直觉。

## 3. 最小示例

### 3.1 只写事件名字符串（零依赖）

```js
export const name = 'my-plugin'
export const inject = []

export function apply(ctx) {
  // ① 重启之前：收尾自己的状态；必要时取消这次重启
  ctx.on('resume-on-restart/before-restart', async (payload) => {
    await flushMyJournal()                       // 同步收尾（宿主会等你跑完）
    if (myMigrationRunning()) {
      // 返回非空值 = 取消；推荐 { cancel: true, by, reason }
      return { cancel: true, by: 'my-plugin', reason: '数据迁移进行中，稍后重启' }
    }
    return undefined                            // 放行
  })

  // ② 开机恢复会话之前：做恢复前准备；必要时取消本次自动恢复
  ctx.on('resume-on-restart/before-resume', async (payload) => {
    if (await myStorageBroken()) {
      return { cancel: true, by: 'my-plugin', reason: '存储校验失败，先别恢复会话' }
    }
    await warmUpMyCache(payload.candidates)      // 只读 payload，别改
    return undefined
  })
}
```

### 3.2 用常量（推荐，避免字符串手写错误）

包已导出子路径 `dsh-resume-on-restart/hooks`（也 re-export 在包根）：

```js
import { HOOK_EVENTS } from 'dsh-resume-on-restart/hooks'

ctx.on(HOOK_EVENTS.beforeRestart, handler)
ctx.on(HOOK_EVENTS.beforeResume, handler)
```

`HOOK_EVENTS = { beforeRestart: 'resume-on-restart/before-restart',
beforeResume: 'resume-on-restart/before-resume' }`；另有 `BEFORE_RESTART_HOOK`、
`BEFORE_RESUME_HOOK`、`DEFAULT_HOOK_TIMEOUT_MS` 与纯函数 `normalizeHookCancel` /
`describeHookCancel` / `buildBeforeRestartPayload` / `buildBeforeResumePayload` /
`runRestartHook`（一般只要常量，其余是实现细节）。

## 4. `resume-on-restart/before-restart`

### 4.1 触发位置（调用链）

```
设置弹窗「重启 DSH」按钮  ─┐
/restart 命令              ├─→ performRestart(origin, delayMs)
restart_harness 模型工具    │       ├─ 1. ctx.serial('resume-on-restart/before-restart', payload)   ← 本事件
注册后守门自动重启          ─┘       └─ 2. restartDsh(...) 写工件 / 拉 helper / 安排退出
```

- 防重入闩（`restartLatch`）在**进入本事件之前**已由入口 claim；因此处理器里不会再
  有第二个重启挤进来。
- 处理器返回取消值后，入口会把闩 release，用户可以立刻再点一次重启。

### 4.2 payload 字段（已冻结，只读）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `event` | `string` | 固定 `resume-on-restart/before-restart` |
| `plugin` | `string` | 固定 `dsh-resume-on-restart`（来源标识，便于日志） |
| `phase` | `string` | 固定 `before-restart` |
| `origin` | `{kind, sessionId?} \| null` | 发起方：`settings-ui` / `command` / `model-tool` / `auto`；`sessionId` 是因果会话（按钮点击没有） |
| `mode` | `'helper' \| 'pid1-exit'` | 重启模式：普通进程走 helper 握手，容器 PID=1 走优雅退出 |
| `delayMs` | `number` | 响应返回后、真正请求退出前的延迟（ms） |
| `instanceId` | `string` | 本进程实例 id（每次启动随机；新实例与它不同即为「换过实例」） |
| `pid` | `number` | 本进程 pid |
| `port` | `number \| null` | 本进程实际绑定的端口（解析不出为 null） |
| `requestedAt` | `string` | 触发时刻（ISO） |
| `candidates` | `Array<{id, at, running}>` | 这次重启后会尝试恢复的候选快照（**advisory**：真正恢复前还会过用户排除、归档、正常结束门） |

### 4.3 取消后的行为

- **不落任何重启工件**：不写 `ror-<id>.status.json` / `restart-identity.json` /
  停机归因存根、不 spawn helper、不安排退出 —— 进程继续正常服务。
- 统一结果对象（HTTP / 命令 / 工具三个入口都收到）：

  ```json
  {
    "ok": false,
    "cancelled": true,
    "mode": "helper",
    "restartId": null,
    "by": "my-plugin",
    "reason": "数据迁移进行中，稍后重启",
    "error": "cancelled by plugin \"my-plugin\": 数据迁移进行中，稍后重启"
  }
  ```

- 入口差异：
  - `POST /api/dsh-resume-on-restart/restart` → **HTTP 409**（冲突，不是 500）；
    客户端弹「重启被插件取消：取消方: … · 原因: …」，与真正的「重启失败」区分。
  - `/restart` 命令与 `restart_harness` 模型工具 → 各自以错误结果返回上面的
    `error` 文案。
  - 守门自动重启 → `console.warn` + 保留武装文件，下一轮评估再试（不会因为一次
    取消就永久放弃）。
- `wake.log` 追加一行：`{ "ok": false, "error": "restart cancelled: cancelled by plugin \"…\": …" }`。

## 5. `resume-on-restart/before-resume`

### 5.1 触发位置（调用链）

```
启动 → detectRestart → 停机归因 + origin 匹配 → 写 boot 记录（restarts.ndjson）
     → ctx.inject(['agents']) → async IIFE
          ├─ 1. ctx.serial('resume-on-restart/before-resume', payload)      ← 本事件
          ├─ 2. 挑候选（近期活跃 / 暂停集合 / 主动注册）→ 过排除、归档、正常结束门
          ├─ 3. restoreCandidates：逐候选 resumeSession + 投递继续提示
          └─ 4. 全部失败 → fallback 唤醒主会话
```

- 只有**检测到重启**（`wasRestart === true`）且配置 `restoreSessions !== false` 时才派发。
- **每次开机只派发一次**：`serviceWaitTimeoutMs` 快等超时后的「后台续等 → 就绪补跑
  候选循环」不会重复派发（续等只是把同一轮恢复继续跑完）。
- 派发时暂停集合（`paused-sessions.json`）还没被消费，`payload.paused` 是消费前的快照。

### 5.2 payload 字段（已冻结，只读）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `event` / `plugin` / `phase` | `string` | 固定 `resume-on-restart/before-resume` / `dsh-resume-on-restart` / `before-resume` |
| `bootAt` | `string` | 本次启动时刻（ISO，与 boot 记录同值） |
| `prevBootAt` | `string \| null` | 上次启动时刻 |
| `downtimeMs` | `number \| null` | 距上次启动的间隔（ms，含正常运行时间，不是停机时长） |
| `reason` | `string \| null` | 重启归因：`restart-button` / `signal` / `crash` / `auto-restart` 等（与 boot 记录 `reason` 同源） |
| `origin` | `object \| null` | 重启来源记录（`type` / `fromInstanceId` / `mode` / `origin.kind` / `origin.sessionId` / `restartId` 等，与 boot 记录同源） |
| `candidates` | `Array<{id, at, running}>` | 本次将尝试恢复的候选快照（`pickRestoreTargets` 同源，**advisory**） |
| `registered` | `string[]` | 主动注册（`register_restart_recovery`）的会话 id |
| `paused` | `string[]` | 暂停集合里的会话 id |
| `excluded` | `Record<string, string>` | 用户排除集合（会话 id → 排除时刻 ISO） |

### 5.3 取消后的行为

- 本次自动恢复**整体跳过**：不挑候选、不 `resumeSession`、不投递继续提示，
  **也不做 fallback 唤醒**（插件要求的是「这次别动会话」，再向主会话投一条通知就违背意愿）。
- `restarts.ndjson` 追加一条（`type: 'resume-cancel'`）：

  ```json
  {
    "type": "resume-cancel",
    "bootAt": "2026-11-07T04:03:52.490Z",
    "at": "2026-11-07T04:03:52.490Z",
    "by": "dsh-maintenance",
    "reason": "维护窗口，本次不恢复会话",
    "detail": "cancelled by plugin \"dsh-maintenance\": 维护窗口，本次不恢复会话"
  }
  ```

  处理器抛错/超时会额外带 `hookError: true` / `hookTimeout: true`（排障时区分
  「插件主动要求取消」与「兜底取消」）。
- 设置弹窗「重启 → 重启日志」：该次 boot 的结果列出现「恢复已取消」徽标，
  展开明细给出取消方与原因（`detail.cancelTitle`）。
- `wake.log` 追加一行：`resume cancelled: cancelled by plugin "…": …`。
- 不影响下一次重启：下次开机重新判断，除非处理器再次取消。
- 已恢复的主动注册条目保持原样（没有恢复发生，所以不会被移除）；「上次重启无法恢复」
  列表也不会因此新增条目（那是给真正尝试过但失败的候选用的）。

## 6. 取消约定（返回值）

| 返回值 | 含义 | 后续处理器还跑吗 |
| --- | --- | --- |
| `undefined` / `null` / `false` | 继续（没意见） | 跑（串行继续） |
| `true` | 取消（无原因） | 不跑 |
| 非空字符串 | 取消，字符串即原因 | 不跑 |
| `{ cancel: true, by?, reason? }` | 取消（**推荐写法**） | 不跑 |
| `{ cancel: false }` | 明确表示不取消 | **不跑**（⚠ 见下） |
| 其它真值（普通对象、数字等） | 取消，原因按 `String(value)` | 不跑 |

> ⚠️ **重要**：cordis 的 `serial` 派发在遇到任何 `isBailed` 为真的返回值时就会
> 停止后续监听器（这是宿主既定语义，本插件不改变它）。所以：
> - 「我同意，请继续，并且让排在后面的插件也能表态」→ 必须返回
>   `undefined` / `null` / `false`；
> - `{ cancel: false }` 只是「不算取消」，但会把串行链截断 —— 后面的处理器不再执行。
>   不要用它来「表态同意」。
>
> 实际含义：**处理器之间按注册顺序排队，任何一个人返回非空值就等于给出了结论**。

## 7. 兜底：抛错与超时都按取消处理（fail-closed）

| 情况 | 处理 | 记录 |
| --- | --- | --- |
| 处理器抛错 / Promise reject | 视为取消 | `error: true`，原因 `… hook error: <message>`；before-resume 会写 `hookError: true` |
| 处理器超过 `hookTimeoutMs`（默认 `10000`，配置项） | 视为取消 | `timeout: true`，原因 `… hook timeout after <ms>ms`；before-resume 会写 `hookTimeout: true` |
| 宿主太旧 / 上下文没有 `ctx.serial` | 静默跳过（放行） | 无 |

**为什么 fail-closed**：重启与会话恢复都是「不可半途而废」的动作。一个处理器抛错往
往意味着它没来得及收尾（状态没落盘、后台任务没停），此时硬着头皮重启比停下来更糟；
超时同理 —— 但也因此**不要**在处理器里做长任务（见第 9 节）。

**代价**：一个写得不好（抛错/卡死）的第三方插件会挡住重启与恢复。排查线索就在上面
表格的日志里：`console.warn` 前缀 `[resume-on-restart]`、`wake.log`、`restarts.ndjson`
的 `resume-cancel`（带 `hookError` / `hookTimeout`）、以及 HTTP 409 的响应体。

## 8. 可观测性与排障

| 位置 | 内容 |
| --- | --- |
| 宿主日志 | `[resume-on-restart] restart cancelled by before-restart hook: …` / `resume cancelled by before-resume hook: …`（`console.warn`） |
| `<stateDir>/wake.log` | `restart cancelled: …` / `resume cancelled: …`（一行一条 JSON，含 `at`） |
| `<stateDir>/restarts.ndjson` | `type: 'resume-cancel'` 条目（`by` / `reason` / `detail` / `hookError?` / `hookTimeout?`） |
| 设置弹窗 → 重启 → 重启日志 | 该次 boot 的结果列「恢复已取消」徽标 + 明细里的取消方/原因 |
| `POST /api/dsh-resume-on-restart/restart` | 取消时 409 + `{ ok:false, cancelled:true, by, reason, error }` |

`<stateDir>` 默认 `<DSH_HOME>/.resume-on-restart`（配置项 `stateDir`）。

## 9. 约束与反例

- ❌ **不要在处理器里等本插件的重启/恢复完成**（例如轮询 `/restart/health` 等新实例）：
  重启正在等你返回，会一直等到超时（然后取消）。
- ❌ **不要做长任务**：默认单处理器上限 10s，超时 = 取消。要跑久任务请异步起任务、
  立刻返回（并自己负责它在新进程里能继续）。
- ❌ **不要修改 payload**：已 `Object.freeze`（含候选数组与内层对象），写入在严格模式下
  会抛错、非严格模式无效。想让本插件改变行为，请在 issue 里提需求，而不是改数据。
- ❌ **不要在 before-restart 里再触发一次重启**：`restartLatch` 已被当前请求持有，
  新请求只会拿到 409。
- ✅ **处理器要快、要幂等、要吞自己的异常**（或干脆让异常冒泡以明确取消）：
  重启可能被连续触发（一次取消后用户重试），处理器会被再次调用。
- ✅ **注册时机随意**：插件 `apply` 里 `ctx.on(...)` 即可；监听器跟随 fiber 生命周期，
  插件禁用/卸载自动失效。注册顺序 = 串行执行顺序（`ctx.on(name, fn, true)` 可插到队首）。
