# 支持插件说明：dsh-resume-on-restart 与其它插件的兼容

> 适用版本：本插件 **0.35.0 起**；被支持的插件 **dsh-im ≥ 5.8.17**
> （能力判断：`ctx.dshIm?.notificationVersion === 1`）。
> 适用对象：想弄清楚「本插件重启 DSH 时，为什么某些 IM 通知没发出来」的
> dsh-im 使用者，以及想复用同一套接法的其它插件作者。
>
> - 本插件侧接线：`lib/im-notify.js`（注册与取消逻辑）、`lib/index.js` 的
>   `performRestart` / `markImPendingRestoreCandidates`（候选集合的写入时机）
> - dsh-im 侧契约：dsh-im 仓库 `docs/被扩展说明.md`（发送前通知提供者扩展点）
> - 公开文档目录：`docs/`（本文件随包发布，列在 `package.json` 的 `files` 里）

---

## 1. 支持哪些插件

| 插件 | 适用版本 | 能力判断 | 不满足时 |
| --- | --- | --- | --- |
| dsh-im | ≥ 5.8.17 | `ctx.dshIm?.notificationVersion === 1` | 完全降级，见第 3 节 |

只支持 dsh-im 这一个插件。关联方式是**消费方**：dsh-im 提供服务与扩展点，本插件
注册一个通知提供者，没有反向依赖——本插件的 `inject` 声明里没有 `dshIm`
（仍是 `['agents', 'tools']`），dsh-im 也不需要知道本插件存在。

## 2. 如何关联

### 2.1 注册了什么

apply 时经动态注入 `ctx.inject(['dshIm'], …)` 注册一个通知提供者（卸载走
`ctx.effect(() => dispose, 'resume-on-restart: dsh-im notification provider')`，
挂在 inject 内层 fiber 上，dsh-im 服务重载即摘除、重载完成再重新注册）：

```js
{
  id: 'resume-on-restart',                      // /^[a-z][a-z0-9-]{1,31}$/
  events: ['completed', 'failed', 'timeout', 'shutdown'],
  resolve(context) { return resolveImNotification(context); },
}
```

`workspaces` 与 `priority` 不传（全部工作区、默认优先级 100）。`startup` 与
`crash` 不订阅：startup 发生在重启之后，是恢复流程的同伴；crash 是上次宿主
异常退出，与本次计划内重启无关，永远不取消。

### 2.2 取消规则（Decision = `{ cancel: true }`）

候选集合指「本次重启将自动恢复的会话 id 集合」，写在进程内模块级集合里：

- **写入时机**：`before-restart` 扩展点钩子全部通过、重启工件开写之前
  （四个重启入口——按钮 / `/restart` 命令 / `restart_harness` 工具 / 守门自动
  重启——共用 `performRestart`，所以四种入口都生效）。
- **集合口径**：与设置弹窗「待恢复列表」同一份 `restartInfoCandidates()`——
  自动候选 ∪ 主动注册，已剔除用户排除、正常结束、归档、冷 subagent 会话；
  `activate: false`（只登记不拉起）的条目不算「将恢复」，不在集合内。
- **清空时机**：进程退出集合自然消失（模块级内存结构，不落盘）；重启失败
  （`restartDsh` 返回 `ok: false`，进程继续活着）时立即清空，恢复正常的
  通知流。重启后新进程集合为空，恢复工作的 completed「结果汇报」通知不受影响。

| 通知 | 条件 | 行为 |
| --- | --- | --- |
| 会话级（`context.sessionId` 非空） | 该 id 在候选集合内 | `{ cancel: true, reason: 'session will be auto-restored after restart by dsh-resume-on-restart' }` |
| 宿主级（`sessionId` 为空） | `event === 'shutdown'` 且候选集合非空 | `{ cancel: true, reason: 'planned restart with sessions pending auto-restore by dsh-resume-on-restart' }` |
| 宿主级 `shutdown` | 候选集合为空 | `null`（没有会话会被恢复，停机通知有信息量，照发） |
| 其余一切 | — | `null`（没意见，dsh-im 照发，fail-open） |

取消的是「整次扇出」（dsh-im 契约口径），发生在去重与限流之前，不消耗配额。
`reason` 只进 dsh-im 的 host 日志。作用窗口就是重启请求到进程退出的这一段：
会话因重启被打断时，它的 completed / failed / timeout 通知是噪音——恢复流程
马上会把它拉起来并注入继续提示，IM 上不需要再报一次「异常结束」。

## 3. 对应插件不存在时（完全降级）

dsh-im 缺失或版本低于 5.8.17 时：**零注册、零日志、零行为差异**。本插件的
重启检测、会话恢复、重启日志、扩展点等全部功能逐字不变。

降级靠三层，每层都有依据：

| 层 | 写法 | 依据 |
| --- | --- | --- |
| 不声明静态依赖 | `inject` 保持 `['agents', 'tools']`，不加 `dshIm` | cordis 4.x 的 inject 声明全部是必须依赖：Fiber 对每个声明项 `_checkImpl`，任一项没有 impl 就把 epoch 置 INACTIVE、apply 永不执行。声明了 dshIm 而宿主没装 dsh-im，本插件整个不会加载 |
| 动态注入 | `ctx.inject(['dshIm'], (scope) => { … })` | 同一 cordis 能力；dsh-im 存在且激活后回调才执行，不存在则回调永不执行。本仓库 webServer 路由接线（0.14.0 起）同一模式 |
| 版本门 | `dshIm?.notificationVersion !== 1` → 返回 null | dsh-im 契约文档的官方降级写法；`notificationVersion` 是 5.8.17 新增的能力版本标记，旧版没有该成员 |

补充两个防御点：dsh-im 对重复 id 注册抛 `Error(code = 'notification-provider-exists')`，
本插件捕获该错误并 `console.warn` 一条（可见降级，不静默吞栈），其它错误原样上抛；
注册返回的 disposer 是幂等的，重复 dispose 无副作用。

## 4. 边界（不做什么）

- 只取消通知，不发送、不改写正文、不追加通知（`Decision` 只会返回
  `{ cancel: true }` 或 `null`）。
- 不碰 `crash` / `startup`：描述符不订阅，resolve 里对 crash 再挡一层是防御性
  的意图声明，就算订阅面以后变化，计划内重启也永远不取消「上次异常退出」的通知。
- 不碰 dsh-im 的 `question` 交互提问卡与 `ctx.dshIm.send` 主动投递——它们本就
  不在 dsh-im 的通知提供者管线里（见 dsh-im 契约 4.7）。
- 候选集合是重启那一刻的快照：实际恢复前宿主还会过 sessionController 等运行时
  门，个别候选恢复失败时，它重启前的通知已经被取消——结果通过本插件的
  「上次重启无法恢复」列表（`GET /unrestored`）呈现，不靠 IM 通知补报。
- 不做跨进程/持久化：注册表与候选集合都是本进程内存结构（与 dsh-im 契约 4.9
  一致），重启后一切重新来过。

## 5. 排障

**现象：重启时某条 IM 通知没发出来，想知道是不是本插件干的。**

1. 看 dsh-im 侧日志（`[dsh-im]` 前缀，debug 级）：
   - `notification (completed) cancelled by resume-on-restart: session will be
     auto-restored after restart by dsh-resume-on-restart`——会话级取消，
     reason 即候选命中；
   - `notification (shutdown) cancelled by resume-on-restart: planned restart
     with sessions pending auto-restore by dsh-resume-on-restart`——计划内
     停机的宿主级取消。
2. 在宿主侧（任意插件 apply 或调试通道）执行
   `ctx.dshIm.listNotificationProviders()`：应能看到
   `{ id: 'resume-on-restart', events: ['completed','failed','timeout','shutdown'] }`。
   看不到 = 没注册成功，按第 3 节排查（dsh-im 版本低于 5.8.17？dsh-im 未激活？）。
3. 没有 `cancelled by` 日志但通知还是没发：那不是本插件——去查 dsh-im 自己的
   目标解析、限流与去重。
4. 本插件侧的降级是**零日志**设计（缺失/旧版不产生任何输出），所以「没有日志」
   本身不构成异常证据；要确认降级状态，用第 2 步的 `listNotificationProviders`
   或直接看 `ctx.dshIm?.notificationVersion`。
